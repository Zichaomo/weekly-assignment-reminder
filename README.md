# 每周作业提醒（北化在线）

自动抓取北京化工大学「北化在线」（THEOL 平台）**所有课程**的作业与在线测试截止时间，
每周日汇总未来 N 天要交的内容，推送到你配置的渠道（默认企业微信群机器人）。

**核心原则：这份提醒是发给全班同学的，所以「我交没交」不参与筛选 —— 一律以截止日期为准。**

> ⚠️ 这条原则不是洁癖，而是踩过坑的结论：平台首页的「待提交作业」是它自己的**动态视图**，
> 一旦你交了某门课，那门课就**整门从视图里消失**。实测同一时刻首页只列 3 门课，
> 而逐门课扫一遍发现 **22 门课有作业、其中 19 门根本没进首页视图**。
> 按旧逻辑，你每交一门作业，全班同学就少收一门课的提醒（复变函数、大学物理实验都这样丢过）。
> 所以本工具**默认全量扫描**，且没有关掉它的入口。

## 快速开始

```powershell
# 1) 首次使用 / 登录态过期时：双击 login.bat —— 自动填充账号密码 + 自动点「登录」，无需你动手
#    （若平台弹滑块，窗口会留着让你拖一下；脚本检测到登录成功就自动保存会话并退出）
# 2) 日常操作（检索 / 添加 / 管理 / 黑名单 / 提前发布）：双击 console.bat（Web 控制台）
#    双击时若服务已在运行，会把已有窗口置于前台，不会开出第二个窗口
#    旧版 WinForms 窗体保留在 console-legacy.bat，作为降级备用
# 3) 每周定时自动推送：已实现（Windows 计划任务，默认跟随 config 的 wecom_webhook）
#    python data\task_register.py --time 09:00     # 注册；改时间就再跑一次
#    python data\task_register.py --run-now        # 立刻验证一次
#    详见「定时」一节（改时间、查状态、切正式群都在那里）
```

## 首次部署（换机器 / 刚 clone 下来必做）

1. 装依赖：`pip install playwright`（**不要** `playwright install`，本项目复用系统 Edge，不下载 Chromium）
2. 建配置：`copy data\config.example.json data\config.json`，再按里面注释填你的推送渠道
   （`data/config.json` 已被 .gitignore 忽略 —— webhook 的 `key=` 就是群发口令，不能进仓库）
3. 登录：双击 `login.bat`。它会自己填账号密码并点「立即登录」。
   **前提是 Edge 里存过北化账号密码**（`data/edge_cred.py` 会从任意 Edge 用户目录的密码库读，
   旧域名存的也算；没存过就第一次手动输一次，浏览器问「保存密码」时选**保存**）
4. **刷新课程表**：双击 `console.bat` → 打开「课程黑名单」→ 点里面的「刷新课程表」
   （这个按钮会真的去平台重扫一遍课程总表，约 10-20 秒），生成 `data/courses.json`
   （课程索引含你账号下的课程编号与名称，属个人数据、不入库，所以 clone 后是空的）
5. 路径：脚本用 `%USERPROFILE%` / `Path.home()` 定位，不写死用户名，换机器直接跑。
   若你的 Python 不在 `%USERPROFILE%\.workbuddy\binaries\python\envs\default\`，改 `data\console.ps1` 第 4 行即可。

> 所有抓取脚本必须用装了 playwright 的解释器：
> `%USERPROFILE%\.workbuddy\binaries\python\envs\default\Scripts\python.exe`
> 系统 python 没装 playwright。**但黑名单相关命令不需要 playwright，用哪个 python 都行。**

## 统一控制台（推荐，一个界面搞定全部）

双击 `console.bat`，**只会有一个 Edge 应用窗口**（无地址栏，观感等同桌面程序），
启动用的那个控制台窗口会在几秒内自动关闭。

| 双击次数 | 行为 |
| --- | --- |
| **第 1 次** | 后台无窗口启动服务 → **等它真的能回答 HTTP** → 再开 Edge 应用窗口 |
| **第 2 次及以后** | 服务已在运行 → **把已有窗口置于前台**，打印提示，**不新建窗口** |
| 服务在跑、但**没有可用窗口** | 直接**新开一个窗口**（见下），绝不让你面对「请自行打开」 |

> **关掉浏览器窗口 = 停止服务**，端口与内存随即释放。

> **为什么第 1 次要先起服务、再开浏览器？**
> 踩过的坑：反过来的顺序（先开浏览器）会让 Edge 在服务还没监听时就请求
> `127.0.0.1:8277`，页面直接是 `ERR_CONNECTION_REFUSED`「拒绝访问」，
> 得手动按刷新。现在启动器会调 `data/wait_ready.py` 等真能回答 HTTP（最多 20 秒）
> 才开窗；20 秒仍未就绪就**什么都不开**并提示你看 `data/server_console.log` ——
> 开一个通向死端口的窗口没有任何意义。
> （探测逻辑刻意不写在 `.bat` 里：批处理的嵌套引号 + 重定向太脆，实测会报
> 「此时不应有 1>」；而且还要避开 TIME_WAIT 残连接造成的误判，见下。）

> **「服务在跑、窗口却不在」这个中间态是怎么来的？**
> 关掉浏览器窗口后，服务靠「心跳停了」才退出，最多有 30 秒延迟（见下一节）。
> 这期间端口仍被占用，但窗口已经没了 —— 窗口标题会退回成 `127.0.0.1` 这类地址串，
> 于是「按标题找窗口并置前」必然失败。旧版在这里只打印一句
> `Console service is already running, but its window was not found`，
> 等于把你丢在一个打不开的控制台前。现在这种情况会**自动新开一个窗口**给你。

### 停止服务的判定方式（进程 + 页面心跳，双条件）

服务端 `--watch-pid <Edge进程号>` 会每 3 秒检查一次，但**只看进程并不可靠**：
当 Edge 已有实例在运行时，`--app` 参数会被交给那个实例处理，
我们启动的进程随即退出 —— 只看进程号会导致服务刚启动就自杀（实测踩过）。

所以退出条件是**两个都成立**：

1. 被守护的 Edge 进程已消失；
2. 页面心跳也停了（`console.html` 每 5 秒 POST 一次 `/api/heartbeat`，超过 30 秒没有心跳）。

所以**关窗后服务最多还会活 30 秒**（等心跳超时）。这 30 秒里端口仍被占用：
此时再双击 `console.bat`，启动器会先失败一次「置前旧窗口」，然后**自动新开一个窗口**，
不会让你卡在「服务在跑但打不开」的状态里（见上一节的说明）。

页面从未连上过的启动瞬间给 180 秒宽限期，避免误判。

其他停止方式（都可以忽略，除非有异常）：

- 页面底部「**停止控制台服务**」按钮；
- 万一没取到 Edge 进程号（服务退化为常驻），关掉 `python.exe` 进程即可。

### 日志与降级

服务日志在 `data/server_console.log`（无窗口运行，出问题时看这个）；
`data/server_error.log` 记录 HTTP 层异常。两个文件都在 `.gitignore` 里。

> 旧版 WinForms 窗体保留在 `console-legacy.bat`（`data/console.ps1`），功能一致、随时可降级。
> 旧窗体标题栏的「脚本构建时间」只对旧版有意义：Web 版每次打开都是新代码，不存在热重载问题。

> **`console.bat` 只输出 ASCII 英文，这是刻意的。** 详见「已知坑 · Windows / PowerShell」一节。

界面分区（Web 版）：

| 位置 | 功能 |
| --- | --- |
| 报头 | 刊名 · 当天日期 · 推送渠道 · 本机服务地址 |
| 操作栏 | **检索北化在线**（全量扫描，约 1-2 分钟，**后台执行不卡界面**，有进度条与计时）· 预览 · 提前发布 · 未来 N 天 · 含全部平台作业 · 抓在线测试 |
| 操作栏右侧 | **课程黑名单** · **测试黑名单** · **选修课**（三个并列的弹窗，加入/移出均需二次确认） |
| 中部 | **手动添加作业**：科目 / 内容 / 截止 / 备注 → 添加 · 清理过期条目 |
| 列表 | 来源（平台/手动）· 科目 · 标题（在线测试 / 手动 / **选修** 徽标）· 截止 · 剩余 · 状态；行内操作：平台行「内容 / 打开」，手动行「编辑 / 完成 / 删除」 |
| 底部 | 两个标签页：**推送预览**（一次显示两条：班级群那条 + 下面「个人小群（完整清单）」）· **运行日志**（含本次抓取用时与分阶段明细） |

要点：

- 「检索北化在线」**一律全量扫描**（默认按截止日期扫全部课程）。想翻已过期的旧作业，勾「含全部平台作业」。
- 选中「平台」行 → 「查看作业内容」读作业正文；「浏览器打开」按状态跳转（已交=查看结果，未交=提交作业）。
- 列表里「平台」行来自北化在线、只读；「手动」行来自 `manual.json`、可管理（双击行即编辑）。
- 抓取完成后日志会打印**本次抓取用时**，含分阶段明细（登录 / 扫描课程）。

## 检索结果复用（5 分钟内不再重复抓取）

一次全量扫描要 **1-2 分钟**。所以「检索北化在线」的结果会**在内存里缓存 5 分钟**，
期间点「预览」或「提前发布」**直接复用**，只需几秒，不会让你为同一份数据等两次。

日志里会明确写出用的是哪一份：

```
正在生成预览（未来 7 天）…
ⓘ 复用了 42 秒前的检索结果，未重复抓取（点击「检索北化在线」可强制刷新数据）
已生成预览（未发送），共 6 条。
```

复用的两个前提（都满足才复用）：

1. 距上次检索**不超过 5 分钟**；
2. 上次检索**覆盖的天数 ≥ 本次需要的天数**（避免拿 7 天的结果去发 30 天的预览而漏条目）。

> **失败的结果永不缓存。** 若某次检索「平台 0 条」或「过半课程抓取失败」，
> 它不会被留作可复用数据 —— 否则一次失败会被伪装成成功，比慢更糟。
> 这种情况会回退为重新抓取，并在日志里说明原因。
> 想立即用新数据：再点一次「检索北化在线」即可（它会刷新缓存）。

## 并发抓取会被自动排队

同一时刻只允许**一个抓取进程**操作平台（抓取时会在 `data/scrape.lock` 留一个锁文件）。原因是两个抓取会共用同一个
`storage_state.json` 与平台会话里的「当前课程」上下文，互相把页面导航搞乱。

实测过一次事故：两个抓取并发时，**18 门课全部报「课程页未出现课程作业入口」**，
耗时 22 分钟、结果 0 条 —— 看起来像登录失效或平台故障，其实是自己撞自己。

所以现在会加一把文件锁（`data/scrape.lock`）：后启动的抓取会等待，
最多等 120 秒，仍拿不到就**带警告继续**（不会让你点了没反应）。
上次崩溃遗留的陈旧锁（超过 10 分钟）会被自动清理。

> 这个场景在真实使用中会遇到：**周日 09:00 定时任务正在跑，你正好在控制台点了检索。**

## 推送文案（紧迫感分级）

每次运行会生成**两条**文案（2026-10-18 起）：

| 文案 | 发给谁 | 内容 | 落盘 |
| --- | --- | --- | --- |
| **班级群那条** | 企业微信群（`channel` + `wecom_webhook`） | 全部课程**减去选修课** | `last_message.txt` |
| **个人小群那条** | 选修课小群（`personal.wecom_webhook`） | **完整清单**，选修课带 `🎓选修` 标记 | `last_message_personal.txt` |

两条各自记账（`push_log` 的 `audience`）、各自去重、各自告警 —— 一条失败不影响另一条。
个人那条的标题是「📚 我的作业提醒（含选修课）」，其余排版规则完全一致：

```
📚 作业提醒 · 未来 7 天（至 10-20）

⚠️ 近两天截止
• 复变函数与积分变换（A）｜26-27第六周作业
   ⏰ 今天 23:59 截止
• 大学物理实验(II)｜迈克尔逊干涉
   ⏰ 明天 14:20 截止
• 英语 📌手动｜U校园 综合3U4
   ⏰ 10-15 23:59 截止（还剩 2 天）
   备注：老师在企业微信群发的

🗓 本周稍后
• 普通物理(Ⅱ)｜第7周作业
   ⏰ 10-16 23:59 截止（还剩 3 天）
• 马克思主义基本原理 📝在线测试｜专题十
   ⏰ 10-17 23:59 截止（还剩 4 天）
• 嵌入式系统创新应用与实践 🎓选修｜第1次：作业题2.1   ← 只在个人那条里出现
   ⏰ 10-23 10:02 截止（还剩 5 天）

—— 共 6 项，详情以「北化在线」为准
```

设计要点：

- **两个分组**：距截止 **≤2 天**的进「⚠️ 近两天截止」，其余进「🗓 本周稍后」；
  某一组为空时**整组消失**（不出现空标题）。组内都按截止时间从早到晚排。
- **倒计时精度按距离递减**，不做无意义的小数点表演：
  | 距截止 | 显示为 |
  | --- | --- |
  | 当天 | `今天 23:59 截止` |
  | 次日 | `明天 14:20 截止` |
  | 2 天内（含零头小时） | `10-15 23:59 截止（还剩 1 天 23 小时）` |
  | 超过 2 天且小时为 0 | `10-16 23:59 截止（还剩 3 天）` |
  | 已过期 | `10-11 14:44 截止（已逾期）` |
- **标记**：手动补录的带 `📌手动`，在线测试带 `📝在线测试`（二者可叠加，如 `📝在线测试｜标题`）。
- **不再包含**：生成时间（对同学是噪音）、以及任何「我已交 / 我未交」状态 ——
  后者是刻意的（见开头的核心原则）。
- 末尾一行合计 `—— 共 N 项，详情以「北化在线」为准`，提醒同学以平台为准。
- 窗口内没有任何待交作业时，只发一句 `✅ 这段时间没有待交作业，安心休息。`

> ⚠️ 已知小瑕疵：剩余时间按**秒**计算，所以「整 3 天后截止」有时会显示成
> `还剩 2 天 23 小时`（因为生成文案的时刻比截止时刻早了几秒）。不影响判断，暂未修。

## 在线测试（与作业同一套规则）


平台把「在线测试」放在另一个栏目，本工具会**一起抓**，并在提醒里用 📝 标注：

```
• 马克思主义基本原理 📝在线测试
   专题九 社会主义的发展与共产主义的最终实现
   ⏰ 截止 2026-12-13 23:59 （还剩 62 天 2 小时）
```

- 判定：测试列表页「开始测试」列有链接 = 还能做；「查看结果」列有链接 = 有答题记录。
- 截止时间用**测试表自己的格式**（`2026-12-13 23:59:00`，ISO 风格），与作业表的中文格式
  （`2026年12月13日 23:59:00`）不同，代码里两套都认。
- **想跳过某门课的测试**（典型场景：实验课的在线测试是多班共用、且要求课前 10 分钟做，没必要进待办）：
  用「测试黑名单」只屏蔽测试，该课**作业照常抓**。

## 两级黑名单 + 选修课（三者语义不同，别混）

脚本**永远不会自己往这些名单里写东西** —— 它只会「建议」，加入必须由你确认。

| 名单 | 作用 | 存在哪 | 加入方式 |
| --- | --- | --- | --- |
| **课程黑名单** | **整门课都不抓**（作业 + 在线测试都跳过） | `data/course_blacklist.json` | 控制台「课程黑名单」勾选候选 →「加入勾选项(需确认)」→ 二次确认；或 `scrape.py --blacklist-confirm <lid>` |
| **选修课** | **照常抓**，但**不进班级群那条提醒**，只发个人小群那条 | `data/electives.json` | 控制台主页「**选修课**」按钮 →「加入选修课（需确认）」；或 `scrape.py --blacklist-elective 嵌入式` |
| **测试黑名单** | 只跳过「在线测试」，作业照抓 | `data/test_blacklist.json` | 控制台「测试黑名单」→ 输入 lid；或 `scrape.py --test-blacklist-add <lid>` |

### 选修课：抓，但只发给我（2026-10-18 改写）

**典型场景**：你选修了「嵌入式系统创新应用与实践」，班里大多数人根本没上这门课 ——
它的作业只对**你个人**成立，放进「发给全班」的提醒里就是纯噪音。
但它对你本人**是真待办**，所以不能像以前那样"整门不抓"（那样连你自己的提醒也没了）。

现在的语义是**换受众，不是换抓不抓**：

```
平台扫描   → 全部课程（含选修课）           # 照抓，一门都不少
班级群那条 → 全部课程 − 选修课               # 同学收到的提醒里没有这门课
个人那条   → 完整清单（含选修课，标 🎓选修）  # 你自己一条不漏，发到「选修课小群」
```

```powershell
& $PY data\scrape.py --blacklist-elective 嵌入式       # 按课程名片段（唯一匹配才生效）
& $PY data\scrape.py --blacklist-elective 26543        # 也可以直接给 lid
& $PY data\scrape.py --elective-list                   # 看当前标记了哪些
& $PY data\scrape.py --elective-remove 26543           # 取消标记（恢复进班级群）
```

控制台里是**独立入口**：主页操作栏右侧三个并列按钮 ——「课程黑名单」「测试黑名单」「**选修课**」。
选修课有自己的弹窗（标题「选修课（照常抓 · 只发个人小群）」），里面只有「加入选修课（需确认）」
与「移出勾选项（恢复进班级群）」两个动作；它**不出现在黑名单弹窗里**，
因为「不抓」和「换受众」是两回事，混在一起容易让人以为标了选修就不抓了。
弹窗里的条目显示为 `只发个人`。

- **与「陈旧 / 无入口 / 暂无作业」的区别**：那三类是程序**按证据推导**的
  （这课本学期有没有作业），选修课是**你的主观声明**（这课跟班里无关）。
  选修课**不会**再出现在「建议拉黑」候选里 —— 拉黑=完全不抓，与"我要跟这门课"矛盾。
- **成本**：多扫几门课（每门约 2 秒）。换来的是你自己的选修课不会再漏。
- **两个名单互不影响**：一门课可以既被拉黑又是选修课，但拉黑优先（不抓就没有任何提醒）。
  界面上「移出勾选项」会把两个标记一起清掉，避免留下半截状态。
- **不入库**：`electives.json` 与黑名单一样在 `.gitignore` 里（各自选修不同）。

### 个人那条提醒发到哪（选修课小群）

班级群与个人小群是**两个不同的企业微信群机器人**，配置在 `config.json`：

```jsonc
"personal": {
  "enabled": true,
  "channel": "wecom",                     // wecom / pushplus / clipboard / none
  "wecom_webhook": "https://qyapi.weixin.qq.com/...key=…",
  "notify_title": "我的作业提醒（含选修课）"
}
```

- **绝不与班级群共用 key**：`personal.wecom_webhook` 与 `wecom_webhook` 相同会被**拒绝**
  （否则选修课又发进班级群，等于没改）。`notify.py --self-test` 会检查并显示两个通道状态。
- **没配就跳过**：`personal` 留空时只发班级群那条，日志里写明"跳过个人推送：未配置"，
  **不会**把它算成失败，也不会影响班级群那条。
- **典型用法**：新建一个只放「一起上这门选修课的同学」的群，把它的机器人 webhook 填进去。
  注意同一门选修课可能有多个教学班（截止时间不同），拉人前先确认是不是同一个班。

### 候选是怎么算出来的

**学期边界**：`>= 8 月` 算本学期起点为当年 8/1；否则为当年 2/1。

候选分**两类**：程序明确**建议**拉黑的，和只给你**参考**的。

| 理由 | 含义 | 程序是否建议拉黑 |
| --- | --- | --- |
| `stale`（陈旧） | 该课最近一次作业截止时间**早于本学期起点** —— 这课本学期没有作业了 | ✅ 建议 |
| `no-homework-entry`（无入口） | **连续 ≥2 次**扫描都没能进入「课程作业」栏目，且从未见过作业 | ✅ 建议 |
| `no-homework-yet`（暂无作业） | 能正常进入课程页、栏目也在，但**连续 ≥2 轮都是 0 条** | ⚠️ 仅供参考 |

门槛都设成 2 次，是为了避免一次网络抖动就把正常课程误杀。

> **「暂无作业」为什么不直接建议拉黑？**
> 因为有些课本学期就**只在期末布置一次作业**，之前一直是空的。自动拉黑它 = 到期末漏掉那次作业。
> 所以程序只把它列出来供你判断，**是否拉黑由你决定**：
> 如果这门课**本学期还有课**，就不要拉黑它。

列表里这两类会**分开显示**：建议拉黑的排在前面（标签 `陈旧` / `无入口`），
仅供参考的排在后面、样式压暗（标签 `暂无作业`），详情里还会再提醒一次。

> ⚠️ 命令行 `--blacklist-confirm all-candidates` **只确认「建议拉黑」那一类**，
> 不会顺手把「暂无作业」的课一起拉黑。确实想连参考类一起确认，用
> `--blacklist-confirm all-including-advisory`。

### 关于「课程总数」为什么比你实际在修的课多

课程索引是按平台**历史记录**累积的（`blen.student.lesson.list.jsp`），
里面有往学期的课、同名不同教学班的重复项（如「形势与政策（I）」有 3 个 lid）、
偶尔还有已失效的幽灵条目（进入会返回「错误！」页）。

所以「索引 45 门 / 已拉黑 27 门 / 剩下 18 门扫描」并不代表你有 18 门在修 ——
18 门里通常只有**几门**是本学期真正有作业的，其余是空的或历史遗留。用上面的候选表逐步清理即可。

### 控制台里的黑名单对话框

- 底部 **「刷新课程表」** —— 真正去平台重扫课程总表（约 10-20 秒，按钮会变「刷新中…」），
  完成后自动重读候选与黑名单。**外层操作栏里那个同名按钮已经去掉**，统一放在这里。
- 左侧列表：编号 + `[陈旧]/[无入口]/[暂无作业]` 或 `[已拉黑]` + 课程名 + lid
- 右侧详情栏：显示选中项的完整信息（理由、最近作业时间、失败次数、确认时间）
- **加入**：勾选「待确认候选」→「加入勾选项（需确认）」→ 再弹一次确认框 → 才写入
- **移出**：勾选「已拉黑 / 已屏蔽」→「移出勾选项（恢复抓取）」→ 二次确认

## 手动补录（老师发在微信群 / 企业微信群的作业）

平台抓不到的作业，手动补一条即可，汇总时会自动合并、带上 📌 标记和备注。

```powershell
# 方式一（推荐）：双击 console.bat → 在「手动添加作业」区填 科目名 / 作业内容 / 截止时间 / 备注，点「添加」
# 方式二：命令行（适合脚本/批量）
& $PY data\manual.py add --course "高等数学" --title "习题 3.1" --deadline "2026-09-17 23:59" --note "老师发在企业微信群"
```

管理命令（老师取消作业、改截止时间、交了标记完成，都走这里）：

```powershell
& $PY data\manual.py list      # 查看全部
& $PY data\manual.py done 3    # 标记 id=3 已完成（不再提醒）
& $PY data\manual.py rm 3      # 删除 id=3
& $PY data\manual.py edit 3 --deadline "2026-09-20 23:59" --title "改后的标题"
& $PY data\manual.py clean     # 清掉 7 天前已过期的条目
```

> 过期作业会自动掉出汇总：手动条目和平台作业一样，只保留「现在 ~ 未来 N 天」窗口内的。
> 只有「截止时间填得不规范、解析不出来」的手动条目才会永久保留（标「未标注」），避免漏掉口头布置的活。

截止时间写法（支持多种格式，只给日期默认当天 23:59）：

| 输入 | 解析为 |
| --- | --- |
| `2026-09-17 23:59` | 2026-09-17 23:59 |
| `2026-09-17` | 2026-09-17 23:59 |
| `2026/9/17 23:59` | 2026-09-17 23:59 |
| `9-17 23:59` / `9/17 23:59` / `9.10 23:59` / `9月10日 23:59` | 当年 9-17 23:59（跨年算明年） |
| `9-17` / `9/17` / `9.10` / `9月10日` | 当年 9-17 23:59 |

## 自动登录（login.bat）

登录态失效时双击 `login.bat` 即可，**正常情况下不需要你输入任何东西**：

1. 用持久 Edge profile（`%USERPROFILE%\.workbuddy\profiles\buct-course-edge`）打开 `sso_login.jsp`。
2. 若会话还有效 → 直接保存 `storage_state.json` 并退出。
3. 否则落到登录页：切到「用户名密码」标签 → **先试 Edge 自动填充**，填不上就从
   **Edge 密码库运行时解密**取账号密码（见下）→ 填进两个输入框 → 点「立即登录」。
4. 登录成功 → 自动保存会话 + 截图 `data/login_result.png` + 关窗口，退出码 0。

### 2026-10-18：平台换成 `sidportal.buct.edu.cn`，自动填充彻底失效

学校把统一认证换了：旧地址 `portal.buct.edu.cn/normal/login-normal.html` 现在 **404**，
`sso_login.jsp` 会 302 到 **`https://sidportal.buct.edu.cn/login`**。
新页面是 Angular 单页，和老实现有六处根本差别：

| 项目 | 旧实现（已失效） | 现在 |
| --- | --- | --- |
| 表单位置 | 跨域 iframe `login-normal.html` | **没有 iframe**，就在主页面里 |
| 默认标签 | 只有一个表单 | 默认停在**「企业微信扫码」**，必须先点「用户名密码」 |
| 账号框 | `input[name=username]` | `#nameInput`（`autocomplete=username`） |
| 密码框 | `input[name=password]` | `input[type=password]`（**没有 name**，`autocomplete=new-password`） |
| 提交按钮 | `button:has-text('登录')` | `#submitBtn`，两个框都有值前一直是 `disabled` |
| 自动填充 | 点一下用户名，Edge 灌值 | **不再可靠**：密码框标了 `autocomplete=new-password`，浏览器不往里填密码 |

所以现在的凭据来源是 `data/edge_cred.py`：从**本机 Edge 自己的密码库**里取
（`Local State` 的 `os_crypt.encrypted_key` 用 DPAPI 解出 AES 密钥，
再用 AES-256-GCM 解 `Login Data` 里的 `v10` 密文；全部走 Windows 原生能力，无第三方依赖）。

- **只在内存里用**：解出来的密码不写文件、不进日志、不进台账，日志里只打印位数。
- **不写死域名**：先找 `sidportal`，再退回 `portal` / `experimental-auth-endpoint`，
  你在旧域名存过的密码、或新域名刚存的那条，都能用。
- **多个 Edge 用户目录都看**：专用 profile 与日常 Edge（`…\Edge\User Data\Default`）都会查 ——
  平时在常用浏览器里登录一次，脚本就能读到。
- 拿不到凭据时**不硬猜**：保留窗口转人工（最多 300 秒）并打印可操作提示。
- **profile 被占用时不再直接失败**：改用临时上下文继续（凭据照样能从密码库取）。
  实测过：计划任务启动那一刻，持久 profile 正被另一个窗口占着，Edge 只回一句
  「已在现有浏览器会话中打开」就退出，3 次重试全废 —— 一次登录都没尝试。

**现在唯一需要你动手的情况**：平台弹验证码（图形码 / 短信 / 滑块）。
这时脚本**不关窗口**，打印提示并继续轮询 300 秒 —— 你在那个窗口里完成即可。


```powershell
& $PY data\login.py             # 自动登录优先，卡住转人工（login.bat 用的就是它）
& $PY data\login.py --manual    # 跳过自动填充，直接人工登录
& $PY data\login.py --no-wait   # 自动提交后只等 45 秒，不转人工（定时任务用）
& $PY data\login.py --check     # 只检查 storage_state.json 是否仍有效
```

> 密码不落盘：脚本只保存登录后的 cookie / storage_state；账号密码仍由 Edge 密码管理器保管，
> 需要时由 `edge_cred.py` 在内存里解密（见上一节）。
> **改过北化密码后**：Edge 里存的是旧密码，自动登录会失败 —— 此时手动登录一次，
> 浏览器问「是否保存密码」选「保存」，之后就恢复全自动。

## 推送渠道

改 `data/config.json` 的 `channel` 字段，可选：

| channel | 说明 | 需要配置 |
| --- | --- | --- |
| `clipboard`（模板默认） | 复制到剪贴板 + 弹 Windows 通知，你 Ctrl+V 到任意微信会话。零配置、零风险 | 无需 |
| `pushplus` | 微信里收到公众号消息。pushplus.plus 扫码关注拿 token | 填 `pushplus_token` |
| `wecom` | 企业微信群机器人 | 填 `wecom_webhook` |
| `wechat` | PC 微信客户端 UI 自动化（**不稳定，不推荐**） | 填 `wechat_target` |
| `none` | 只落盘，不推送（演练用） | 无需 |

> **班级群走上面这个 `channel`；选修课那条（个人小群）走 `personal` 段**，两者独立配置，
> 见「个人那条提醒发到哪」一节。`personal` 留空 = 只发班级群那条。

自检配置是否就绪：

```powershell
& $PY data\notify.py --self-test
```

输出会分两段：当前渠道（班级群）与「个人小群通道」，各自显示 `[可用]/[缺配置]/[就绪]/[未启用]`。

### 推送台账与去重

- **台账**：每次真发出/被跳过都会往 `data/push_log.jsonl` 追一条记录
  （时间 / 来源 `weekly`|`hub` / **`audience`（class=班级群 / personal=个人小群）** / 渠道 /
  **目标群** / 是否成功 / 内容哈希 / 字节数 / 首行）。
  以后再出现「莫名多一条提醒」，一眼就能看出是谁、什么时候、发到哪、发了什么。
  `audience` 是 2026-10-18 加的：两条消息各自成功/失败都要能单独查，
  否则「个人那条没发出去」会被「班级群那条成功」掩盖。
- **去重**：`config.json` 的 `dedup_window_sec`（默认 300 秒）内，若已向**同一目标**推送过
  **完全相同**的内容，则跳过并记为 `duplicate-skipped`。目的是防止手滑连点两次「提前发布」。
  - 去重键是「内容 + 目标群」，所以「测试群发过」不会影响「班级群正常发」；
    个人小群的键带 `personal:` 前缀，两条消息**不会互相判重**。
  - 想强制重发同一条：`notify.py ... --no-dedup`。

> 测试群 / 正式群可以分开配：`wecom_webhook` 放当前要用的，`wecom_webhook_prod` 留一个备份。
> 测试时用测试群，发正式消息前把 prod 那条复制到 `wecom_webhook` 即可。

### 检索台账（抓了什么）

推送台账记的是「**发了什么**」，检索台账记的是「**抓到了什么**」——
两者分开，因为「没收到提醒」可能是抓取失败，也可能确实没作业，得能区分。

每次抓取（控制台「检索」/「预览」/「提前发布」，以及定时任务）都往
`data/fetch_log.jsonl` 追一条：

| 字段 | 含义 |
| --- | --- |
| `source` | `hub-list`（检索按钮）/ `hub-preview` / `hub-publish` / `weekly`（定时） |
| `days` / `mode` | 窗口天数（9999 = 全部）与取数口径（`deadline-only` / `pool`） |
| `platform` / `tests` / `manual` | 抓到平台作业多少条、其中在线测试多少、手动补录多少 |
| `rows` | 进入最终窗口的条数 |
| `elapsed_sec` | 本次抓取耗时 |
| `cached` / `data_age_sec` | 是否复用了缓存、缓存是多久前的 |
| `failed_count` / `failed_courses` | 有几门课抓取失败（覆盖不完整时能立刻发现） |
| `ok` / `error` | 成功与否及错误原因 |

查看方式：

```powershell
& $PY data\fetch_log_show.py      # 最近 10 条
& $PY data\fetch_log_show.py 30   # 最近 30 条
```

> 它解决过的问题：曾出现「黑名单候选突然消失」，当时分不清是抓取失败还是数据被覆盖；
> 也出现过「推送说平台 0 条」，看不出是登录态失效还是真没作业 —— 有了这份账就能一眼判断。

## 失败告警（定时任务的前置件）

> **为什么先做告警、再做定时**：本工具的失败是**静默**的 —— 群里没消息，和
> 「这周真的没作业」在表面上一模一样。定时任务一旦静默失败，你可能漏掉两周作业才发现。
> 所以自动化之前必须先让失败**出声**。

### 铁律：告警绝不发到班级群

作业提醒是发给**全班同学**的，告警是发给**你自己**的。两者必须分开配置，
否则一次抓取失败就会把「自动登录失败 / 抓取异常」这类技术文字轰到班级群里。

所以告警默认渠道是 **`local`**：写 `data/last_alert.txt` + 弹一条 Windows 通知，
**不碰任何群**。要用企业微信，必须显式改成测试群：

```jsonc
"alert": {
  "enabled": true,
  "channel": "local",          // local=本机通知(推荐) / wecom_test=测试群 / wecom_prod=班级群(慎用)
  "fallback_channel": "local", // 主渠道失败时的降级目标
  "local_style": "balloon",    // balloon=托盘气泡(自动收回) / dialog=消息框(必须点掉) / both / auto
  "cooldown_sec": 3600,        // 同类告警该窗口内只发一次
  "interval_days": 7,          // 「该跑没跑」阈值：7 天 + 12 小时
  "grace_hours": 12
}
```

### 本机通知长什么样

`channel=local` 时，**屏幕右下角弹一个托盘气泡**：警告图标 + 标题
（如「作业提醒：抓取失败」）+ 一行摘要，约 10 秒后自动收回，不需要点它。
完整正文同时写进 `data/last_alert.txt`。

想要一个**必须点掉**的：`--style dialog`，或把 `local_style` 改成 `dialog`。

> **为什么不用系统自带的 WinRT toast？**（2026-10-16 实测）
> 原来那套 `Windows.UI.Notifications` + `CreateToastNotifier` 在这台机器上**已经失效**：
> 报 `The process has no package identity. (HRESULT: 0x80073D54)` ——
> 新版 Windows 不再允许**没有 MSIX 包标识**的进程弹 WinRT toast。
> 更糟的是旧代码把失败吞掉了、照样 `return True`，台账里一路记着 `sent=true`，
> **通知其实一次都没弹出来**。这就是典型的静默失败，也正是这个模块要消灭的东西。
>
> 现在改用 WinForms 托盘气泡（不需要包标识，实测可用），并且**通知失败就如实返回失败**
> （退出码 2、台账 `sent=false`）。兜底顺序：气泡 → 消息框 → 把 `last_alert.txt` 推到台前，
> 保证告警不会彻底消失。
>
> 另外，所有内嵌 PowerShell 统一用 `-EncodedCommand`（base64 / UTF-16LE）传参：
> 既避开引号嵌套，也避开「无 BOM 的 `.ps1` 被 Windows PowerShell 5.1 按 GBK 读」——
> 后者实测会让脚本里的中文直接变成语法错误。

- `wecom_test` 用 `wecom_webhook`（测试群），`wecom_prod` 用 `wecom_webhook_prod`（班级群）。
- **`wecom_prod` 会把同学拉进你的运维现场**，除非确实需要否则别用。

### 什么时候告警

| 触发 | kind | 级别 | 为什么算失败 |
| --- | --- | --- | --- |
| 登录失效且自动登录也失败 | `login-failed` | error | 本次没生成提醒，群里不会有消息 |
| 抓取子进程非 0 退出 / 抛异常 | `fetch-crashed` | error | 同上 |
| 扫了课但平台 **0 条** | `fetch-empty` | error | 全部课程都没作业的可能性极小，更像会话失效或改版 |
| **过半课程**抓取失败 | `fetch-partial` | error | 覆盖严重不完整，漏报风险高 |
| 推送失败（webhook/token 失效等） | `push-failed` | error | 提醒没发出去 |
| 到点没跑成功 | `missed-run` | error | 定时任务本身没工作 |

**故意不告警的情况**：个别课程失败（只警告）、以及「窗口内确实没作业」——
后者会正常发一条「✅ 这段时间没有待交作业，安心休息」，那是正常结果不是故障。

### 「该跑没跑」怎么判

```powershell
& $PY data\weekly.py --check-freshness                  # 只看，不发
& $PY data\weekly.py --check-freshness --alert-if-stale # 陈旧就发告警（挂到计划任务/登录补跑上）
& $PY data\alert.py --check-freshness --notify
```

判定用的是**台账**，不是某个状态文件：距最近一次 **`source=weekly` 且成功**的记录
超过 `interval_days + grace_hours` 就告警。

> **只认 `source=weekly`**：手动点「提前发布」写进台账的是 `hub-*`。
> 如果把手动也算成功，那「定时任务其实一次都没跑过」就永远查不出来 ——
> 这正是本项目此前的真实状态（`fetch_log` 里 weekly 只有一条演练记录）。

### 告警自己的台账

每条告警都往 `data/alert_log.jsonl` 追一条（时间 / kind / 级别 / 是否送达 / 渠道 /
内容哈希 / 首行），运行记录在：

```powershell
Get-Content data\alert_log.jsonl -Tail 5     # 最近 5 条告警
& $PY data\alert.py --self-test              # 打印告警配置与「该跑没跑」状态，不发送
```

冷却状态在 `data/alert_state.json`（按 kind 记时间），所以**同一类问题连续出现不会
变成每天一条骚扰**；但换了一类问题（kind 变了）会立刻发。

> 手动发一条测试：
> `& $PY data\alert.py --title "测试" --detail "正文" --kind manual-test --channel clipboard`
> （`--channel clipboard` 只进剪贴板，不会打扰任何人。）

## 定时

定时分两部分，**两部分都已生效**（都是 Windows 计划任务）：

| 部分 | 作用 | 状态 |
| --- | --- | --- |
| **① 每周日的定时推送** | 每周日 09:00 抓取 + 推送（默认跟随 config 的 `wecom_webhook`） | ✅ 已实现并实测通过 |
| **② 周日开机后的补推检测** | 检查本周日是否已推送，没推则补推 | ✅ 已实现并实测通过 |

> **两者发到哪个群，只看 `config.json` 的 `wecom_webhook`**（默认 `--wecom config`）。
> 你在那里放测试群就发测试群，换成正式班级群就发正式班级群，**不需要重新注册任务**。
> 测试时想临时只发测试群，注册时加 `--wecom test`。

### 第一部分：每周日的定时推送

一条命令注册好（默认**跟随 `config.json` 的 `wecom_webhook`**，即你配哪个群就发哪个群）：

```powershell
& $PY data\task_register.py --time 09:00            # 每周日 09:00，跟随 config 的 wecom_webhook
& $PY data\task_register.py --time 09:00 --dry-run  # 只看会注册什么，不真注册
& $PY data\task_register.py --time 09:00 --wecom test   # 只发测试群（测试时用）
& $PY data\task_register.py --query                 # 查看任务状态与下次运行时间
& $PY data\task_register.py --run-now               # 立刻触发一次（验证用）
& $PY data\task_register.py --unregister            # 删掉任务
```

改时间＝用新 `--time` 再跑一次（`/F` 覆盖同名任务，不会注册出两个各发一次）。
**改群不用重新注册**：任务运行时会重新读 `config.json`。

任务名固定 `BUCT-Homework-Weekly`，实际执行的是
`python data\task_run.py --wecom config --days 7 --target-time 09:00`：

| 环节 | 谁做 | 说明 |
| --- | --- | --- |
| **幂等闸** | `task_run.py` | 今天已成功推过群 → **秒退不发送**（重复触发才敢开） |
| 选目标群 | `task_run.py` | **默认跟随 `config.json` 的 `wecom_webhook`**；测试时用 `--wecom test` 强制测试群 |
| 抓取/汇总/排版/推送 | `weekly.py` | 业务逻辑一行都不重复实现 |
| 登录自愈 | `weekly.py` 的 `ensure_login()` | 会话过期时自己调 `login.py --no-wait`（实测 10-50 秒能自愈） |
| 失败告警 | `alert.py` | 抓取 0 条 / 过半失败 / 推送失败都会出声 |
| 记账 | `data/task_log.jsonl` | 几点跑的、多久、退出码、抓到多少条、**发到哪个群** |

**重复触发（2026-10-18 加）**：`09:00` 起**每 10 分钟再试一次，持续 2 小时**（09:00–11:00）。
这一层是给下面这种真实情况兜底：09:00 那一刻电脑刚开机、还停在登录界面，
交互式任务起不来（见「漏发复盘」）。重复触发**不会连发** ——
`task_run.py` 开头会先问「今天已经发过没有」，发过就秒退（台账记 `reason=already-pushed-today`）。

**错过了会补跑**：任务设了 `StartWhenAvailable`，周日那一刻没开机/休眠，开机后系统会补跑一次。
（这与第二部分是两件事：这里是系统级补跑，第二部分是业务级「这周到底发出去没有」。）


#### 测试群 / 正式班级群，到底在发哪一个

`config.json` 里有三个企业微信 key。**先看这张"谁读哪一条"的表**：

| 谁在发 | 读哪个字段 | 怎么决定 |
| --- | --- | --- |
| **周日定时任务**（第一部分） | **`wecom_webhook`** | 默认 `--wecom config`：**跟随 config.json** |
| **周日补推任务**（第二部分） | **`wecom_webhook`** | 同上（注册时默认 `--wecom config`） |
| 控制台「提前发布」/「检索预览」 | `wecom_webhook` | `config.json` 的 `channel` + 该字段 |
| `notify.py` 命令行 | `wecom_webhook` | 同上，或 `--channel` 覆盖 |
| 定时任务「只发测试群」（测试用） | `wecom_webhook_test` | 注册/运行时显式 `--wecom test` |
| 显式发正式群 | `wecom_webhook_prod` | `--wecom prod` 或 `alert.channel=wecom_prod` |
| 失败告警（默认） | 不走群 | `alert.channel: local` → 只发本机通知 |

**一句话**：**所有推送（含周日定时任务与补推）都看 `wecom_webhook`** ——
你在那里放测试群就发测试群，换成正式班级群就发正式班级群。
`wecom_webhook_test` 只在「这次要专门发测试群」时才用（`--wecom test`）。

- **想发正式群**：把 `wecom_webhook_prod` 的值复制到 `wecom_webhook` 即可，
  **定时任务不用重新注册**（它下次运行会重新读 config）。
- **想退回测试**：把 `wecom_webhook` 换回 `wecom_webhook_test` 的值。
- **认尾号最快**：`…896a828b` = 测试群，`…e73e` = 正式班级群。
- 想知道「这次到底发哪个群」：注册时打印，运行时也打印
  （`data/task_run.log` 里那行「目标群：…」）。

> **为什么默认是 `--wecom config` 而不是钉死某个群**：
> 群的选择权只留在一个地方（`config.json`），你换了 key 就全局生效，
> 不会出现「控制台发新群、定时任务还在发旧群」这种最难发现的错。
>
> **测试时怎么不打扰同学**：注册时用 `--wecom test`，
> 它会强制读 `wecom_webhook_test`，并且**严格模式**——该字段为空就报错停止，
> 绝不会退回 `wecom_webhook`（那可能正是班级群）。
> 注册时还会检查「测试群和主用那条是不是同一个 key」，是同一个就中止
> （说明"测试群"根本没分开，确认无误可加 `--force`）。

> 想确认**某次实际发到哪**：看 `data/task_log.jsonl` 的 `wecom` / `target` 字段
> （`wecom=config` 表示跟随 config；`target` 只留 key 尾号），
> 或看 `data/task_run.log` 里那行「目标群：…」。

#### 两个实测踩过的坑

1. **计划任务里不能写 shell 重定向**。最初把命令写成
   `python task_run.py … >> log 2>&1`，结果 `>>` 被当成 python 的参数，
   argparse 报错退出 2 —— 表现是「任务显示跑过了，但日志文件根本没被创建」。
   现在日志由 `task_run.py` 自己写 `data/task_run.log`，不依赖 shell。
2. **必须用装了 playwright 的那个解释器**。`task_register.py` 会自动探测
   `%USERPROFILE%\.workbuddy\...\envs\default\Scripts\python.exe`，找不到就报错，
   不会静默注册一个跑不起来任务。

### 第二部分：周日开机后的补推检测

第一部分只在**那一刻电脑开着**时才跑得成。周日上午没开机、或者开机了但锁屏导致
自动登录失败，这一周的提醒就没了 —— 而且没人会发现。第二部分负责兜住这个：
**开机登录后检查「本周日到底推出去了没有」，没推就补推。**

一条命令注册好：

```powershell
& $PY data\task_register.py --catchup                    # 仅周日触发 + 错过补跑 + 跟随 config（默认等 15 分钟）
& $PY data\task_register.py --catchup --delay-min 15 --target-time 09:00 --wecom test
& $PY data\task_register.py --query --name BUCT-Homework-Catchup
& $PY data\task_register.py --unregister --name BUCT-Homework-Catchup
```

> `--target-time` 必须与第一部分的定时时间一致（现在是 **09:00**）。改定时时间时两处都要改。

### 这两个任务在系统里到底在哪

两个任务都在**任务计划程序库的根目录**（`TaskPath = \`），不在任何子文件夹里。
Catchup 的触发器会显示成「每周」（实际只在周日），Weekly 也是「每周」。
打开方式任选一种：

| 方式 | 操作 |
| --- | --- |
| 图形界面 | `Win+R` → 输入 `taskschd.msc` → 回车；左侧点最上面的 **「任务计划程序库」**，中间列表里就能看到 `BUCT-Homework-Weekly` 与 `BUCT-Homework-Catchup` |
| 控制台 | `schtasks /query /tn BUCT-Homework-Weekly /v /fo LIST` |
| PowerShell | `Get-ScheduledTask -TaskName "BUCT*"` |

> **找不到时的常见原因**：① 左侧停在「任务计划程序(本地)」而不是「任务计划程序库」；
> ② 中间列表需要往下翻（按名称排序，`B` 开头其实很靠前）；
> ③ 用中文关键字搜「每周」是搜不到的 —— 任务名是英文的 `BUCT-Homework-*`，按名字找。
>
> 本项目没有用 `schtasks /TN` 的文件夹语法（`\子目录\任务名`），所以两个任务就是平铺在
> 库的根目录下，`--query` 输出的 `\BUCT-Homework-Weekly` 那个开头的反斜杠就是根的意思。

任务名 `BUCT-Homework-Catchup`，**仅周日触发**：
每周日 00:05 + `StartWhenAvailable`（那一刻没开机就下次可用时补跑）。
每次触发都会判断要不要动作 —— 不需要动作时**秒退**，不会白等：

| 周的哪一天 | 时间 | 今天推过没 | 判定 | 动作 |
| --- | --- | --- | --- | --- |
| 非周日 | 任意 | — | `not_sunday` | 退出（不等待） |
| 周日 | 早于计划时间（≤90 分钟） | — | `too_early` | **等到「计划时间 +15 分钟」再判定**（2026-10-18 改） |
| 周日 | 早于计划时间（>90 分钟） | — | `too_early` | 退出，交给定时任务（凌晨开机时不该占着进程） |
| 周日 | 已过计划时间 | 已成功推送 | `done` | 退出（这就是「检测」本身） |
| 周日 | 已过计划时间 | 没推成功 | `due` | **等到计划时间 +15 分钟（或开机后 15 分钟）再补推** |

> **`too_early` 为什么不再直接退出**（2026-10-18 的真实漏发）：那天 08:21 开机，
> 补推任务判定 `too_early` → 退出；而 09:00 那次定时任务因为「机器刚开机、还停在
> 登录界面」没跑成 —— 两条路都没接手，群里一整天没有消息。
> 现在只要离计划时间不到 90 分钟，就等到「计划时间 + delay」再判定一次。


#### 2026-10-18 漏发复盘：那天 09:00 为什么群里没消息

不是单一故障，是**三处问题叠加**，每一处单独都足以让一周静默。时间线（全部有台账/事件日志）：

| 时间 | 发生了什么 | 证据 |
| --- | --- | --- |
| 08:20:53 | 补推任务被 `StartWhenAvailable` 补跑（周日 00:05 那个触发点当时没开机） | `task_catchup.log`：判定 `too_early` |
| 08:20:53 | 旧逻辑：`too_early` → **直接退出**，把机会让给定时任务 | 同上 |
| 08:25:44 | 系统关机 | System 日志 Kernel-Power 109 |
| 08:59:44 | 开机 | Kernel-Boot 12 |
| **09:00:00** | Weekly 触发点到了，但机器**还停在登录界面**（09:00:23 才登录）。任务是 `Interactive`，没有交互会话就起不来 → Windows 记 `NumberOfMissedRuns=1` | `Get-ScheduledTaskInfo` |
| 09:00:23 | 用户登录，**Weekly 并没有因此自动补跑** | 同上（NextRunTime 已跳到下周） |
| 09:07:08 | 手动补推：登录态已失效，自动登录按旧版找 `login-normal.html` iframe → 找不到 | `task_run.log`「没找到登录表单」 |
| 09:08:52 | Weekly 其实补跑了一次，但仍然死在登录（且那一刻持久 profile 被另一个窗口占用，浏览器根本没起来） | `task_run.log` `TargetClosedError: … browser has been closed` |
| 09:13:15 | 登录修好后补推成功 → 群里收到 5 项 | `push_log.jsonl` / `task_log.jsonl` |

对应的三处修复：

1. **触发时刻没有交互会话** → Weekly 触发器加「每 10 分钟重试、持续 2 小时」，
   登录之后还有机会（`task_register.py --repeat-min/--repeat-hours`）。
2. **重复触发会连发** → `task_run.py` 加幂等闸：今天已成功推过就秒退。
3. **补推提前退出** → `too_early` 在 ±90 分钟内改为等到「计划时间 + delay」再判定。
4. （另加）**登录改版** → 见「自动登录」一节，凭据改从 Edge 密码库取。

#### 为什么不是「仅周日登录时触发」

**Windows 原生做不到。** 登录触发器的 schema 里只有 `UserId` / `Delay` / `Enabled`,
**没有 `DayOfWeek`**，也没有「Weekly + Logon」这种组合（实测 PowerShell 的
`New-ScheduledTaskTrigger -AtLogOn` 根本不接受星期参数）。

用「登录时触发」就等于**每次开机登录都跑一次**：非周日那次虽然无害（脚本 0.2 秒退出），
但字面上不是"只在周日"，还会在任务计划程序里显示成「登录时」。

所以改成 **Weekly(Sunday) + StartWhenAvailable**：
- **只在周日存在**：周一~周六根本没有触发点；
- 周日那一刻电脑开着 → 到点触发，脚本自己等到「09:00 + 15 分钟」再动作；
- 周日那一刻没开机 → `StartWhenAvailable` 在**下次可用时**补跑，
  也就是你周日开机登录后的正常会话里执行 —— 这正是「开机后约 15 分钟」的来源。

> 脚本里的「只在周日」判断依然保留，作为触发器语义的兜底与**可测**的判断点
> （`task_catchup.log` 里能看到每次的判定结论）。

> 解释器用的是 **`pythonw.exe`**（无窗口版）：`python.exe` 每次运行会闪一个黑框，
> 而这个任务周日可能被触发多次。pythonw 一样能跑，子进程输出照样被
> `task_run.py` 捕获并写进日志 —— 实测 `Last Result=0` 且日志正常落盘。

#### 判定为什么不能复用「该跑没跑」

`alert.check_freshness()` 问的是「距上次成功超过 7 天了吗」，它**答不出
「今天这个周日到底发没发」**。实测反例：上周日成功了、这周日失败了，
距今只有 7 天，`check_freshness` 会判"正常"，但本周提醒根本没发出去。

所以补推用的是独立的 `alert.weekly_due()`：按**日历日**比较
「今天（周日）有没有成功推送到群」，而不是按距今多少小时。

> **"成功推送到群"只认企业微信 / pushplus 的记录**。剪贴板、本机通知、`none`
> 都不算 —— 否则一次「落盘成功」就会被当成"已经通知过全班了"。

#### 实测过的细节

- **登录触发必须用 `LogonType: Interactive`**：PowerShell 的
  `New-ScheduledTaskPrincipal` 默认是 S4U，**不加载用户配置文件**，
  `Path.home()` 会指向系统目录，`login.py` 就找不到 Edge 的持久 profile，
  自动登录必然失败。这个坑很隐蔽 —— 任务会"跑成功"但永远登不上。
  `task_register.py --catchup` 已显式指定，可用 `--query` 复核。
- **为什么是登录触发而不是开机触发**：抓取要拉起 Edge，需要一个**已登录的交互式桌面**；
  系统刚启动还没人登录时跑，必然失败。登录触发天然满足这个前提。
- **不重复补推**：补推成功后再触发本脚本，`done` 分支就会拦住它。
- **不和定时任务撞车**：`--delay-min 15` 给定时任务留出发车时间；
  万一两个抓取真的重叠，也有 `scrape.py` 的文件锁排队，脚本还会检查
  任务台账里有没有「刚启动还没结束」的记录，有就跳过。
- **去重会把紧跟其后的补推标记为 `duplicate-skipped`**（这是对的）：
  实测定时任务 12:52 送达后，补推在 12:56 尝试（相距 235 秒 < 300 秒去重窗口），
  内容与目标都相同 → 跳过，群里不会收到两条一样的提醒；
  窗口过后（实测 12:58）补推就能真正送达。**注意**：这种情况下
  `push_log.jsonl` 记的是 `ok=true` + `note=duplicate-skipped`，
  而 `task_run.log` 会写「已发」——想确认"到底有没有真送达"，看 `note` 字段。

### 原方案（WorkBuddy 自动化）已失效

曾在 WorkBuddy 自动化面板里配过一个任务「北化在线作业周报」
（`rrule = FREQ=WEEKLY;BYDAY=SU;BYHOUR=9;BYMINUTE=0`，即每周日 09:00）。
但事件记录显示它**从创建当天（9 月 9 日）起就没有再触发过**，
表里的 `next_run_at` / `last_run_at` 均为空，运行记录只有创建那一次。

更要紧的是：**推送台账里从来没有一条 `source=weekly + channel=wecom`** ——
群里收到的每条提醒都是手动点「提前发布」发出的。也就是说这条路从未真正打通过。

### 当初的候选方案（已定案：A + B）

原来列了四个候选，现在**已按 A + B 落地**，记在这里是为了说明为什么这么选：

| 方案 | 做法 | 结果 |
| --- | --- | --- |
| **A. Windows 计划任务** | 注册每周日的计划任务；勾「错过尽快启动」 | ✅ **已采用** —— 就是「第一部分」 |
| **B. 登录时补跑** | 检查「本周是否已成功推送」，没有就补发 | ✅ **已采用**（等价形式）—— 就是「第二部分」 |
| **C. 常驻守护进程** | 隐藏进程常驻，到点触发并负责重登/重试 | ❌ 未采用：为一个每周一次的任务多养一个常驻进程不划算 |
| **D. 半自动** | 每周手动点一次「检索 + 提前发布」 | ❌ 未采用：依赖人记得，而漏发的代价是全班收不到 |

B 项的落地形式与当初设想略有不同：不是「登录时补跑」这个触发器
（Windows 没有「仅周日登录」这种触发器），而是
**Weekly(Sunday) + StartWhenAvailable** —— 周日那一刻没开机就下次可用时补跑，
效果等价且触发点本身就只在周日。详见「第二部分」。

### 三个无论如何都要注意的前提

1. **登录态只有约 3 天寿命**（`TGC` / `JSESSIONID` 都是会话级 cookie），
   而定时是每周一次 —— 执行时登录态几乎必然已失效。
   `weekly.py` 的 `ensure_login()` 会先自动尝试登录一次（最多 45 秒，不转人工），
   实测能自愈成功；但它需要**真的创建一个可见的 Edge 窗口**，
   所以执行那一刻电脑必须是**已登录、未锁屏**的状态。锁屏时的表现是：
   任务照常启动，但自动登录失败 → 触发失败告警 → 由第二部分补推兜住。
2. **抓取/推送失败会告警**（见「失败告警」一节）：登录失效、抓取崩溃、平台 0 条、
   过半课程失败、推送失败、以及「该跑没跑」都会走 `alert.py` 出声。
   但**告警只在任务真的被执行时才会发** —— 如果压根没触发（原 WorkBuddy 方案就是
   这样），就需要 `weekly.py --check-freshness --alert-if-stale` 这类外部检查来兜住。
   所以告警是定时的前置件，不是替代品。
3. **推送目标是显式参数，不继承配置**：定时与补推都默认发**测试群**
   （`--wecom test`），发正式班级群必须显式 `--wecom prod`。
   这样你为了测试去改 `config.json` 的 `wecom_webhook`，也不会让周日那次误发全班。

直接正则取 `name="\d+_content"` 的 `value` 再 HTML 解码即可，不必进 ueditor iframe。


## 双击 .bat 弹出「无法验证发布者」（低完整性标签）

**现象**：双击 `console.bat` 弹出「打开文件 - 安全警告 / 无法验证发布者。
你确定要运行此软件吗？」，发行商显示「未知发布者」。文件本身完全正常。

**原因**：文件被打上了 Windows 的 **Low 完整性标签**（`Mandatory Label\Low Mandatory Level`）。
完整性标签是「不能向上写」的强制标记，资源管理器启动低完整性对象前会要你确认。
**不是**「从网上下载」那类 —— 这些文件上没有 `Zone.Identifier`。

本机的成因（2026-10-16 实测）：受限沙箱会话把**工作区根目录**标成了 Low，
之后在这个目录里新建/修改的文件都会**继承**它 —— 当时 `console.bat`、`README.md`、
`.gitignore` 中招，而 `data/` 下的旧文件仍是 Medium。

**判断方法**（一条命令看清全工作区）：

```powershell
& $PY data\fix_integrity.py           # 只扫描，报告带 Low 标签的对象
& $PY data\fix_integrity.py --list    # 顺带列出清单
```

**修复**：

```powershell
& $PY data\fix_integrity.py --fix           # 修复
& $PY data\fix_integrity.py --fix --dry-run # 先看会改哪些
```

修复做法是「**原样删除重建**」：先给父目录设成 Medium（这一步允许），
再让文件重新继承父目录的标签。内容一个字节都不改，重建前后逐字节校验，不一致立即回滚。

> **为什么不能用 `icacls` / `Set-Acl` 直接改？**（都试过，都失败）
> - `icacls <file> /setintegritylevel Medium` → `Access is denied`
> - PowerShell `Set-Acl -Audit` → `需要 SeSecurityPrivilege`（管理员才有）
> - `SetNamedSecurityInfo(LABEL_SECURITY_INFORMATION)` → 返回 5（拒绝访问）
>
> 原因是这些对象的写权限来自沙箱身份而非登录用户，所以「所有者」也没法直接改标签。
> 能给目录设标签、且新文件会继承父目录标签 —— 这才是能走通的那条路。

**怎么避免再次发生**：让**工作区根目录一直是 Medium**。标签是继承的 ——
根目录一旦被标成 Low，之后在里面新建的每个文件都会继承它。所以：

1. 修好后，根目录与新文件都回到 Medium，就**不会再弹**这个警告；
2. 万一又出现（例如某次受限会话又把根目录标了 Low）：跑一次
   `fix_integrity.py --fix` 即可，**不需要重装、不需要改注册表、不需要管理员**；
3. 别去右键属性勾「解除锁定」—— 那是给「从网上下载」的文件去 `Zone.Identifier` 的，
   对付不了完整性标签（这两个东西经常被混为一谈，实测本机文件根本没有那个标记）。

## 已知坑（都是实测踩出来的）

### 平台侧

- **首页「待提交作业」视图不可信**：交过的课会整门消失。别改回依赖它取课程列表。
- **`hwtask.jsp?lid=<lid>` 直连不可用**：服务器忽略 URL 里的 lid，按会话里的「当前课程」渲染，
  6 个不同 lid 会全部返回同一门课的作业。必须先 `enter_course.jsp?lid=<lid>&t=hw` 进课程页切换当前课程。
  好在**复用同一个页面直接 goto 即可**，不必为每门课开新窗口（旧写法慢 5 倍，且依赖主页面停在 SSO 首页）。
- **平台有两套时间格式**：作业表是 `2026年11月26日21:13:00`，测试表是 `2026-12-13 23:59:00`；
  还见过残缺秒 `9:04:0`。`norm_deadline()` 三种都处理，改动时别退回单一格式。
- **偶发空作业表**：页面跳过去了但表格没渲染，会解析出 0 条。而 0 条本身是合法结果
  （有的课确实没作业），所以**必须重试**，否则静默丢数据。现在会自动重试 2 次。
- **在线测试入口层级特殊**：`course_column_preview_transfer.jsp` 的真实路径在 `/meol/jpk/course/`，
  手拼 `/meol/course_column_preview_transfer.jsp` 会 404。菜单文字的 `textContent` 带换行和缩进
  （实测是 `'\n在线测试\n'`），匹配前必须去掉空白。
- **入口必须是 SSO**：`https://course.buct.edu.cn/meol` 是未登录首页，正确入口是
  `/meol/homepage/common/sso_login.jsp`。**`login.py --check` 也不能访问 `/meol` 做判定**，
  否则会话有效也会误报 NEED_LOGIN。
- **课程作业链接每课不同**（`…?columnId=xxxxxx`），必须从课程页菜单动态取。

### 登录侧

- **登录态会过期**：CAS 的 `CASTGC` / 门户的 `TGC` 是长效票据但不保证长期有效。
- **2026-10-18 平台改版**：统一认证换到 `sidportal.buct.edu.cn`（Angular 单页、无 iframe），
  旧 `portal.buct.edu.cn/normal/login-normal.html` 已 **404**。新页要：先点「用户名密码」标签、
  用 `#nameInput` / `input[type=password]`、最后点 `#submitBtn`（两个框有值前是 `disabled`）。
  详见「自动登录」一节。
- **Edge 自动填充在新域名上不可靠**：密码框标了 `autocomplete="new-password"`，浏览器不填密码；
  而且自动填充绑的是 **origin**，新域名永远命不中旧域名那条记录。所以凭据改从 Edge 密码库取
  （`edge_cred.py`），自动填充只作为"优先尝试"。
- **持久 profile 会被占用**：另一个 Edge 窗口（含 login.bat 自己开着的那个）占着它时，
  `launch_persistent_context` 抛 `TargetClosedError`，Edge 只回一句「已在现有浏览器会话中打开」。
  `login.py` 现在会退回临时上下文继续，不再整体失败。
- **登录页有验证码风控**（图形码 / 短信 / 滑块）。实测本机 IP + 常用设备下不弹；
  万一弹了，脚本保留窗口并轮询，人工过一次即可，不要试图自动过。
- **别改回「有死代码的 main」**：login.py 曾有一段永远执行不到的分支
  （`if args.check:` 后直接 `return`，紧跟的 `if args.auto:` 成了死代码），
  表现为「自动填充成功但从来没点过登录按钮」。改完必须实跑验证。


### 服务与并发

- **不要在抓取进行中再点检索**：会与正在跑的抓取互相干扰（已加文件锁自动排队，
  但排队超时后仍会继续，结果可能不准）。定时任务跑的时候同理。
- **缓存只存健康结果**：平台 0 条或大面积失败的结果不缓存，避免把失败伪装成成功。
- **服务停止方式**：**关掉浏览器窗口即可** —— 服务按「浏览器进程消失 **且** 页面心跳停止」
  两个条件判定（约 30 秒内退出），释放端口；也可点页面底部「停止控制台服务」。
  端口固定 `127.0.0.1:8277`（只监听本机，局域网访问不到）；
  **重复双击 `console.bat` 不会起第二个实例**，只会把已有窗口置于前台。
- **服务是无窗口运行的**：看不到控制台窗口是正常的。它的输出在 `data/server_console.log`
  （`run_hidden.vbs` 用 `python -u` 启动，否则块缓冲会让日志迟迟不落盘），
  HTTP 层异常在 `data/server_error.log`。
- **改完 `server.py` 必须重启服务**：它是常驻进程，改动不会热加载。
  关掉浏览器窗口再双击 `console.bat` 即可（旧的 `console.ps1` 同理）。
- **启动器必须「先起服务、再开浏览器」**（2026-10-15 修，实跑验证）：
  反过来的顺序会让 Edge 请求到一个还没监听的端口，页面直接
  `ERR_CONNECTION_REFUSED`「拒绝访问」，用户得手按刷新。
  现在启动器调 `data/wait_ready.py --timeout 20` 等到真能回答 HTTP；仍未就绪就报错并
  指向 `server_console.log`，**不开窗** —— 通向死端口的窗口只会给一个错误页。
- **判「服务在不在」要看 LISTEN，不能看「能不能连上」**：主动关闭方留下的
  `TIME_WAIT` 残连接同样能 `connect_ex` 成功，于是**已经退出的服务被误判成还在跑**，
  启动器就走进复用分支、再也开不出窗口。`wait_ready.py` 因此只用
  `connect_ex` 的结果配合「是否真的在 LISTEN」来判断，并用 `settimeout` 保证
  快速返回（曾经在死端口上每次等满 TCP 超时，号称 20 秒实际让用户等了 78 秒）。
- **「服务在跑、窗口不在」时要自动开新窗口**：关窗后服务还有最多 30 秒才退出，
  这期间端口被占用、窗口已消失（窗口标题会从 `作业提醒控制台` 退回成 `127.0.0.1`），
  「按标题置前」必然失败。旧版只打印 `its window was not found` 让用户自己开；
  现在这种情况直接新开一个窗口。**窗口标题是置前功能的唯一依据，别只测「页面能开」。**

### Windows / PowerShell

- **改完 console.ps1 要关窗重开**：PowerShell 不会热重载脚本。窗口标题栏的构建时间就是判断依据。
- **`console.ps1` 必须是 UTF-8 with BOM**：PowerShell 5.1 读无 BOM 的 .ps1 会按 GBK 解析中文，
  首行 `Add-Type` 直接失效、整个窗体起不来。用编辑器改完记得确认 BOM 还在。
- **变量作用域要当心**：`$full` 曾只在 `Fetch-Platform` 里定义，`Publish` 引用它得到 `$null`，
  `-not $null` 恒为 true → 发布路径永远走 `--pool` 漏课。函数内要用就在函数内自己算。
- **批处理文件只用 ASCII，中文由别的通道输出**（这一条踩了三遍，务必照做）：
  - cmd 按**系统 OEM 代码页**（中文系统 GBK）解析 `.bat` 本身。
    往 `.bat` 里写 UTF-8 中文，会被当成非法命令并打印
    「'...' 不是内部或外部命令」；写在文件里的 `chcp 65001` 来不及救
    —— 解析发生在它生效之前。
  - 让 Python 打印中文同样不稳：`GetConsoleOutputCP()` 与 `chcp` 可能**不一致**
    （本机实测：`chcp` 说 936，Python 读到 65001），于是按 65001 写 UTF-8、
    控制台按 936 渲染 → 乱码。全局的 `PYTHONUTF8` / `PYTHONIOENCODING`
    也会干扰子进程的输出编码。
  - 结论：**启动器（`console.bat`）只输出 ASCII 英文**，`chcp 936` 仅用于让环境一致。
    ASCII 不会被任何代码页弄坏。网页界面照旧全中文，不受影响。
  - 验证这类问题时**不要用管道**（`cmd /c xxx > file`）：Python 检测到输出被重定向
    会改用 UTF-8，把真实控制台里的问题掩盖掉。要用真实的控制台窗口测
    （`Start-Process cmd`），并检查**原始字节**是否与代码页匹配。
- **PC 微信 4.x 是 Qt 渲染**，uiautomation 取不到控件树，UI 自动化实测走不通，别再投入时间。

## 性能参考

18 门课（27 门已拉黑）的实测数据：

| 阶段 | 耗时 |
| --- | --- |
| 登录 / 建会话 | 约 4 秒 |
| 扫描 18 门课（每门课同时取作业 + 在线测试） | 约 60-125 秒 |
| **合计** | **约 1-2 分钟** |

优化历程：154 秒 → 119 秒（合并两个栏目、一次进页面）→ 65 秒（复用页面、去掉多余跳转、
无测试栏目快速放弃）。剩下的开销是平台强制的（每门课必须真的进一次课程页）。
**再想提速只有一个方向：减少扫描课程数 —— 也就是用黑名单。**
