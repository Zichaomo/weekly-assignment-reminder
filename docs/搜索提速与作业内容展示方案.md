# 搜索提速与作业内容展示方案

日期：2026-10-25  
状态：设计建议，尚未实施。

## 1. 建议采用的方向

把一次“搜索作业”拆成三个可以分别完成的步骤：**立即显示本地结果 → 后台更新所有课程的列表 → 逐条补齐本次需要的作业正文**。图片作业以原图和裁剪预览为依据，OCR 辅助提取，重复要求默认折叠。

这同时解决两个问题：用户不用等整个扫描结束才能查看作业；新增的正文和图片处理也不会继续拉长列表等待时间。

建议分阶段做：

1. **先改善等待体验并减少真实耗时**：持久化列表缓存、真实进度、修复测试开关、优化等待与重试。
2. **再让每条作业自动显示文字和图片**：正文缓存、后台补齐、原图预览和手动裁剪。
3. **最后减少人工整理**：按课程识别重复要求，使用带坐标的 OCR 建议作业区域；复杂版面再考虑可选的视觉模型。

全量扫描的覆盖原则继续保留：没有被用户拉黑的课程都要检查，不因“我已经交了”或“最近没作业”而跳过。第一版不建议引入同一平台会话内的多课程并发。

## 2. 项目现状与判断依据

### 2.1 当前结构

本次阅读了 README、抓取与控制台主流程、正文提取、汇总与推送相关代码，并查看了本地检索台账的时间和统计字段。未运行在线抓取、未发送消息，也没有读取账号凭据内容。当前仓库没有 `docs` 目录，本文件建立该目录。

| 层次 | 主要文件 / 函数 | 当前职责 |
| --- | --- | --- |
| 控制台 | `data/console.html` | 发起任务、轮询、显示列表和推送预览 |
| HTTP 服务 | `data/server.py` | 单线程长任务队列、内存缓存、HTTP 接口 |
| 业务衔接 | `data/hub.py` | 组装抓取参数、转换列表、取正文、预览和发布 |
| 平台抓取 | `data/scrape.py` | SSO 建会话、逐课程切换、作业与测试列表解析 |
| 汇总 | `data/weekly.py` | 调用抓取子进程、合并手动作业、按截止日期筛选、区分受众 |
| 推送与定时 | `data/notify.py`、`data/task_run.py` 等 | 分渠道发送、去重、定时执行、告警与台账 |

控制台搜索链路：

```text
console.html → POST /api/tasks（fetch）
             → server.run_task → hub.run_list
             → weekly.fetch → scrape.py 子进程
             → SSO → 逐门课进入课程页 → 作业列表 / 测试列表
             → 整轮 JSON 返回 → build_rows → 前端显示
```

有几条已经验证过的业务约束必须保留：

- 首页“待提交作业”会因个人提交状态漏掉整门课，不能作为完整课程来源。
- `hwtask.jsp?lid=...` 不能代替进入课程页；平台依赖服务端会话中的“当前课程”。
- 课程黑名单、测试黑名单、选修课分别控制抓取范围、测试范围、推送受众，不能混用。
- 班级群排除选修课；个人小群保留完整清单。
- 手动作业继续使用现有录入、完成、编辑和删除流程。

### 2.2 当前到底有多慢

README 的性能参考是“18 门课，约 60–125 秒”。本机 `data/fetch_log.jsonl` 中，从 2026-10-16 到本次阅读时，满足 `ok=true`、`cached=false` 且有耗时的记录共 15 条：

| 指标 | 台账中的值 |
| --- | --- |
| 中位数 | 35.9 秒 |
| 平均值 | 40.54 秒 |
| 最短 / 最长 | 34.4 / 77.1 秒 |
| 最近一次定时抓取（2026-10-25） | 35.2 秒 |

这些记录的课程配置和调用入口不完全相同，不是严格的性能对照实验；它们说明当前常态已接近半分钟，但偶发等待仍明显。缓存复用记录的 `elapsed_sec` 可能沿用原抓取耗时，不能把它当成预览本身的耗时，因此统计时已排除。

README 最后写“再提速只有减少扫描课程数”。从现有代码看，这个结论过于绝对：固定等待、空表判断、正文会话复用和请求方式仍有优化空间，但具体收益需要实测。

### 2.3 发现的具体问题

| 位置 | 已确认的行为 | 影响 |
| --- | --- | --- |
| `scrape._run_scan`、`sweep_all_courses`、`fetch_course_both` | SSO 后固定等 4 秒；每课结束默认等 1 秒；每个列表页另等 0.3 秒 | 持续叠加，与实际页面就绪时间无关 |
| `fetch_course_both` | 作业解析为空就重跑整门课，最多 3 次；此前可能先等“截止时间”15 轮 | 真正没有作业的课程也可能消耗大量时间，并重复抓测试 |
| `wait_text` | `timeout` 实际是循环次数，循环内还有 `inner_text` 超时与休眠 | 名义上的超时不是严格墙钟时间上限 |
| `server.run_task`、`cache_get` | 搜索始终重新抓；5 分钟内存缓存主要供预览和发布使用 | 重开控制台、重复搜索仍需等待；定时任务结果不能直接复用 |
| `GET /api/list`、`hub.run_list(fetch=False)` | 本地读取只构造手动作业列表 | 即使本机曾抓到平台作业，重开窗口也无法立即恢复完整列表 |
| `weekly.fetch`、前端 `runTask` | 子进程输出整轮结束才返回；前端只有一个轮询变量，等待期间禁用多个按钮 | 后台执行虽不阻塞浏览器，但不能逐课显示，也不适合再加入正文后台任务 |
| `hub.run_content` | 每个未缓存的正文请求重新启动浏览器、走 SSO、固定等 4 秒 | 挨个点正文会重复支付启动成本 |
| `get_hw_content`、`html_to_text` | 已拿到正文 HTML，但转文本时直接去掉标签 | 纯图片正文可能被显示为“没有填写正文”；附件和布局信息丢失 |
| `--with-content`、`hub.build_rows` | 抓取侧串行补正文且只留文本；平台行转换没有透传正文 | 仅打开这个已有参数，既会更慢，也不能直接实现目标界面 |

还有三处应在改造前修正或明确的语义：

1. **“不抓在线测试”开关实际可能无效。** `hub` 传入 `--no-tests`，但 `_run_scan` 用 `args.with_tests or args.deadline_only` 决定是否抓测试；默认截止日期模式会把显式关闭覆盖。应改成三态：未指定时按模式决定，显式开/关优先。
2. **“含全部平台作业”没有真正包含过期条目。** 目前用 `days=9999` 扩大未来窗口，`build_rows` 仍要求 `now <= deadline`。新缓存和界面需把 `include_expired` 与未来天数拆开。
3. **互斥锁并非严格互斥。** `FetchLock` 等待 120 秒后会带警告继续；超过 10 分钟的锁也会仅凭时间清理。正文和 `hub` 刷新课程入口没有统一经过这把锁。新增后台任务前必须统一协调，否则会放大已有串课风险。

## 3. 搜索提速：体验与真实耗时分别优化

### 3.1 先显示缓存，再刷新，明确新旧程度

首次部署没有缓存时，显示真实扫描进度；有缓存时，打开控制台立即显示上次结果和已缓存正文，并标注更新时间。

建议交互：

- **打开控制台**：读取本地列表，不自动登录平台。上次内容立即可读。
- **检索北化在线**：保留旧列表，后台启动或复用正在进行的刷新任务；每完成一门课就更新对应行。
- **切换未来天数 / 是否显示过期项**：优先对已保存的完整列表本地筛选，不重复访问平台。
- **刷新单门课 / 重试失败课程**：提供局部刷新入口，执行相同的课程切换和校验。
- **刷新正文**：独立于列表刷新，供老师修改了正文而标题不变时使用。

页面状态示例：

```text
显示上次结果，更新于 09:01；正在检查最新作业：7 / 12 门课程
列表检查完成：12 / 12；正在补齐正文：3 / 5
11 / 12 门已更新，1 门失败；失败课程继续显示上次结果
```

缓存“可用于查看”和“可直接用于正式发布”必须分开：

| 场景 | 建议处理 |
| --- | --- |
| 日常查看 | 可以展示旧数据，明确更新时间及覆盖范围 |
| 刚搜索完后预览 | 使用本次列表，不为补正文重新全量抓取 |
| 正式发布 / 定时推送 | 要求列表满足新鲜度与覆盖检查；否则先刷新 |
| 刷新失败 | 保留旧列表供查看；禁止自动把它包装成本轮最新、完整结果 |
| 正文或 OCR 失败 | 保留有效标题与截止时间，显示“正文暂不可用”；不阻断正常提醒 |

第一版建议仍以 **5 分钟**作为发布时列表新鲜度的初始配置，沿用用户已经熟悉的口径；查看缓存不受此限。正式发布应默认要求本次所需范围完整，失败时保留预览并告警，不能发送“这段时间没有作业”的假结论。若以后支持人工发布不完整清单，应明确显示缺失课程并单独记录。

### 3.2 持久化完整列表，按课程保存成功状态

建议新增一个本地 SQLite 缓存文件 `data/cache/homework.sqlite3`，原始图片单独保存在 `data/cache/assets/`。使用 Python 标准库 `sqlite3`，无需数据库服务；现有黑名单、配置和手动作业 JSON 暂不迁移。

选择 SQLite 是为了处理控制台与定时进程同时读写、按课程提交结果、正文关联和版本更新。第一版不需要额外缓存服务。

核心规则：

- 保存解析到的完整列表，再在展示和推送层按日期筛选；不要只缓存“未来 7 天”的结果。
- 缓存记录带账号范围标识、平台、课程索引版本、解析版本以及作业/测试覆盖信息。账号标识不包含密码或会话票据。
- 每门课的作业、测试分别记录 `checked_at / status / error`；“未抓测试”“测试被屏蔽”“测试确认空”是不同状态。
- 单门课成功解析后用事务更新该范围；失败不把旧记录清空。
- 同一次扫描的覆盖集合、成功集合、失败集合分别保存，不能只看总条数是否大于零。
- 成功的新列表中缺失的旧条目可以标记为本轮已不在列表，但仅在确认列表完整、无遗漏分页时执行；失败或疑似截断时不删除。
- 课程黑名单移出后，需要重新抓取该课才能声称覆盖完整；测试范围扩大时同理。
- 选修课变更只需重新计算推送受众，不应重抓平台。手动条目每次读取最新状态。
- 缓存中的合法空结果可以保留，但必须有“已登录、结构有效、范围完整、确实为空”的证据。当前代码的“0 条不缓存”是保守保护，不能直接去掉。

历史 `hw.json` 和 `courses.scan.json` 不应直接视为权威新缓存：前者没有接入当前统一读写链路，后者主要保存扫描统计。新缓存由后续成功扫描生成。

### 3.3 去掉无效等待，保留可靠判断

不要把所有 `sleep` 一律删掉。建议逐项替换：

| 当前等待 | 改造方式 |
| --- | --- |
| SSO 后固定等 4 秒 | 等待已认证页面特征和实际可访问的平台页面；仅有 Cookie 名称不足以证明会话可用 |
| 每个列表页固定等 0.3 秒 | 等待目标表格/明确空态；验证最终 URL、课程上下文和表头，再解析 |
| 每课固定等 1 秒 | 从保守的可配置最小间隔开始试验，例如 0.2–0.5 秒；遇限流或错误升高时退避，必要时恢复原值 |
| 空作业表反复整课重试 | 区分有效空表、登录跳转、结构异常、加载超时；仅异常重试，并尽量重试失败栏目 |
| 所有失败使用相同长等待 | 用单调时钟设置单步骤与单课程总预算，避免多个超时叠加数分钟 |

若扫描 18 门课且每课都抓两个列表，现有显式休眠的理论累计约为 `4 + 18 × (1 + 0.3 × 2) = 32.8 秒`，还不含空表重试和网络时间。这只是代码路径上的估算，并非当前每次运行都一定承担这些等待，也不意味着能全部消除。

对“连续两次没有测试入口”的自动跳过增加过期时间或周期复查。当前 `no_test_streak >= 2` 会持续跳过，老师后来添加入口时需要能重新发现；人工测试黑名单则继续遵守用户选择。

### 3.4 第二步实验：用 HTTP 取列表与正文，浏览器负责认证和回退

现有列表和正文是 JSP 页面，正文还放在隐藏输入域中，因此值得验证能否直接获取 HTML，减少浏览器页面渲染成本。**这是待验证路径，不能承诺平台一定支持。**

Playwright 的 `browser_context.request` 与浏览器上下文共享 Cookie，可用现有登录状态发请求。该能力已在[官方 APIRequestContext 文档](https://playwright.dev/python/docs/api/class-apirequestcontext)核实，但“共享 Cookie”不代表服务端课程上下文相互隔离。

建议试验顺序：

1. 浏览器走已有 SSO 登录路径，确认平台会话有效。
2. **串行**请求 `enter_course.jsp?lid=...&t=hw` 切课，从返回页面提取栏目链接。
3. 请求动态发现的作业/测试栏目地址，跟随重定向，校验并解析返回 HTML。
4. 验证正文页隐藏域能否通过 HTTP 取得。
5. 如果需要前端脚本执行、返回登录页或结构不符，在该步骤回退现有浏览器实现，记录原因。

不要硬编码 `columnId`，不要重新尝试已知无效的 `hwtask.jsp?lid=...` 直连，也不要假定平台存在尚未发现的 JSON API。课程入口仍需执行；省下的是页面装载与等待，而不是绕过服务端要求。

浏览器回退路径可试验屏蔽非必要字体、媒体等资源。Playwright 提供[网络监控与路由能力](https://playwright.dev/python/docs/network)，但实际拦截范围必须以正确性对照为准：不能阻断认证或列表脚本，正文图片下载也必须单独保留。

### 3.5 所有平台访问共用一个协调入口

保留同一平台会话内的串行访问，不把现有 `ThreadPoolExecutor(max_workers=1)` 简单改大。

- 控制台重复点击同范围刷新，返回已有任务 ID，不再新增相同扫描。
- 定时任务和控制台通过同一跨进程锁协调；超时返回“正在忙 / 等待超时”，不能无锁继续。
- 锁回收需核验持有者身份和存活状态，不能只凭文件年龄。长任务可维护心跳，释放锁时校验所有权。
- 扫描、正文下载、刷新课程表、认证及登录态更新都走相同协调规则；浏览器句柄由所属工作线程创建和使用。
- 本地读缓存、文本整理和已下载图片的 OCR 不占用平台访问锁，可以另用小型后台队列；初始 OCR 并发设为 1，避免影响用户正常工作。
- 第一版每轮列表扫描与紧接其后的正文下载共用一个已认证上下文。列表已提交缓存并可显示后，才执行正文阶段；完成后释放浏览器。暂不引入长期常驻浏览器。
- 正文按小批次处理，在安全的课程边界允许高优先级列表请求先执行；每次重新进入平台流程都显式设置课程上下文。

复制同一份 `storage_state.json` 创建多个 BrowserContext，可能仍指向同一服务端会话，不能据此证明可并行切课。多独立会话并发放到后续研究，第一版不依赖它获得收益。

## 4. 作业内容展示：先保真，再精简

### 4.1 每条作业的显示形式

在现有标题单元格下增加内容区域，避免横向再增加很多列：

```text
普通物理｜第八周作业                    截止：周五 23:59
内容：教材 P128，第 3、5、8 题
[作业区域缩略图]  [展开正文]  [原图 / 完整要求]  [调整裁剪]
内容核验于 09:02 · 通用要求已折叠
```

示例中的课程、页码、题号仅用于说明交互，不是本次提取结果。

| 正文类型 | 默认展示 | 展开后 |
| --- | --- | --- |
| 纯文字 | 本次任务、页码、题号或正文前几行 | 保留段落、列表、表格的完整正文 |
| 纯图片 | 作业区域缩略图；尚未定位时展示原图缩略图 | 原图、裁剪选择、可选 OCR 文本 |
| 图文混排 | 保持原始顺序的文字与图块 | 完整图文，不把两者打散拼接 |
| 图片只有一小块是作业 | 裁剪区域，并标注“已裁剪，可查看原图” | 原图及折叠的通用要求 |
| 只有附件 | 附件名称、类型、打开入口 | 第一版不自动解析所有 Office/PDF 附件 |
| 正文未获取 / 获取失败 | “正文正在加载 / 暂不可用” | 重试与平台原文入口 |

没有可靠摘要时，就展示原始文本或图片，不根据标题猜内容。在线测试第一版只展示列表中已有说明信息，不自动点击“开始测试”获取试题，以免启动考试或消耗次数。

### 4.2 正文提取应保留结构

扩展现有 `get_hw_content`，不要再仅返回 `content_text`：

1. 保留解码后的原始 HTML，供追溯及重新解析；正确处理实体，避免反复解码破坏原文。
2. 用 DOM/HTML 解析器读取隐藏输入域，减少对属性顺序的依赖。
3. 按文档顺序生成内容块：段落、列表、表格、图片、附件；保留题号、公式图片、脚注和图片说明。
4. 图片和附件相对地址按详情页基址解析成绝对地址；必要时识别已验证的懒加载属性。
5. 原始材料只读；摘要、裁剪和折叠结果另存，不覆盖来源。

建议内容块结构：

```json
{
  "item_key": "platform:account-scope:course-id:homework:homework-id",
  "content_status": "ready",
  "source_checked_at": "2026-10-25T09:02:00+08:00",
  "source_hash": "sha256-of-normalized-source",
  "revision": 2,
  "blocks": [
    {"id": "p1", "type": "paragraph", "text": "完成教材指定习题"},
    {"id": "i1", "type": "image", "asset_id": "sha256-of-image-bytes"}
  ],
  "summary": {"text": "", "method": "extractive", "source_block_ids": []},
  "display_regions": [
    {"asset_id": "sha256-of-image-bytes", "box": [0.08, 0.15, 0.92, 0.42], "origin": "manual"}
  ],
  "folded_block_ids": [],
  "review_status": "unreviewed"
}
```

`box` 使用经过方向纠正后的原图坐标，四个值为 `[x1, y1, x2, y2]`，归一化到 0–1；它不是 `[x, y, width, height]`。支持同一图片多个矩形，避免题目分散在图中时只能保留一个区域。

`source_hash` 用于识别正文结构变化，图片另用内容字节哈希。完整内容版本应同时关联正文及图片哈希，避免图片地址不变但老师替换了图片时仍沿用旧裁剪。

### 4.3 自动加载正文，但不拖住列表

列表完成后，为当前展示窗口中的作业安排正文任务，优先级依次为：用户正在查看的条目、临近截止的新作业、其余缺失或过期正文。旧作业和历史条目按需加载。

```text
课程列表扫描 → 每课成功结果写入缓存 → 界面可读
                                 ↓
                当前窗口中缺正文 / 需复核的作业入队
                                 ↓
               详情 HTML → 内容块 → 图片下载 → 本地缓存
                                 ↓
                 界面显示图文 → 后台建议摘要和裁剪
```

需要同时修改数据链路：抓取层保留结构化内容，缓存层按作业键关联，`hub.build_rows` 返回摘要、状态和资产引用，前端逐条更新。只改爬虫或只加一列都不够。

第一版可采用的默认策略：

- 已有正文立即显示；未过期正文不重新下载。
- 正文复核 TTL 初始设为 6 小时，做成配置；明确标注核验时间，承认 TTL 内可能存在修改尚未发现的窗口。
- 标题、截止时间变化时提前复核，但**标题没变不代表正文没变**。
- 临近截止或发布带正文摘要前，优先复核将展示/推送的内容；内容未及时完成时退回标题与截止时间。
- 支持单条强制刷新；图片优先条件请求，服务器不支持验证器时到期重新下载并比较字节哈希。
- 正文源或图片变化后，旧裁剪和人工摘要标记“需复核”，不悄悄套用到新版本。
- OCR 和摘要处理按“源版本 + 处理器版本 + 规则版本”缓存；规则改变可在本地重处理，不必重新扫描课程。

6 小时是初始产品取舍，不是平台保证。先记录实际修改频率，再调整。

### 4.4 重复要求：默认折叠，不永久删除

用户不想看的通常是每周相同的提交格式、命名方式、拍照要求。但“重复出现”并不等于“本次不重要”：同一题号、同一实验步骤也可能每周都必须做。

建议按可靠程度递进：

1. **人工确认的课程规则优先。** 用户把某一段标记为“该课程通用要求”，后续同课程精确或高相似匹配时默认折叠；可一键恢复。
2. **跨作业比较只生成候选。** 对同一课程多份不同作业的文字块、OCR 块、重复图块做比较。首次识别只提示候选，不自动把疑似题目隐藏。
3. **特殊变化保留。** 重复段落中新增或变化的题号、页码、日期、数量、提交方式、否定词和例外说明，应展开突出；不能被相似度阈值吞掉。
4. **重复图块辅助定位。** 相同模板的页眉页脚可以辅助识别区域，但新的图像版本要重新验证，不能仅按“截掉上面 70%”处理。

界面将正文分成“本次任务”和“通用要求（已折叠，可展开）”。折叠结果记录规则来源与匹配依据，原文始终可见。人工改动优先于自动结果，并绑定源版本。

### 4.5 图片中只有一小部分是作业：三层实现

**第一层：原图 + 手动框选，最先交付。**

- 显示原图缩略图；支持拖动矩形、多区域选择、撤销与恢复原图。
- 保存坐标和图片版本，后续搜索直接复用；导出/预览由原始像素裁剪产生，不重新绘制公式或题干。
- 可为某课程保存“常见区域”作为下一次建议框，但新图片必须校验尺寸与版式，不直接当成已确认结果。

这一步已经能满足“只展示图片里那一部分作业”的核心需求，不依赖 OCR 达到很高准确率。

**第二层：带坐标的 OCR + 版面区域建议。**

- OCR 输出文字、置信度及文字框；按阅读顺序聚成段落和版面块。
- 识别“本周作业 / 习题 / P… / 第…题”等任务线索，结合课程通用要求候选，提出应展示的区域。
- 保留区域中的公式、图形及相邻说明；文字识别框不能作为图文内容的全部边界。
- 裁剪区域带适当留白，跨栏或不连续区域可多选；预览必须可回看原图。
- 低置信度、手写、模糊、复杂公式等情况保留原图并标记“建议人工选择”。

OCR 主要帮助“找到哪里是作业”，不承担把所有题目重写成文字的责任。第一版只定义可替换的 OCR 适配接口，拿实际样本评估中文、公式、版面能力及 CPU 占用后再定具体引擎。

**第三层：可选视觉模型，处理规则和 OCR 难以判断的版面。**

只对新图片或复杂失败样本使用，输出候选区域、来源依据与简短提取文本；做坐标范围、覆盖范围校验，保留人工修正。不能让模型编造题号、补题干，或把“作业要求”全部当噪音去掉。

默认本地处理。如果以后启用云端视觉服务，应提供明确开关和数据发送范围，只传必要的作业图块，不传登录态、Cookie 或包含其他个人信息的整页截图。模型不可用时仍能用原图和手动裁剪完成工作。

## 5. 数据、接口与任务设计

### 5.1 最小数据模型

| 数据 | 关键字段 / 用途 |
| --- | --- |
| `scan_runs` | 扫描 ID、范围、开始结束时间、配置版本、覆盖状态、失败课程 |
| `course_scan_state` | 账号、课程、栏目、最后成功时间、本次状态、耗时、是否完整 |
| `assignments` | 账号 + 平台 + 课程 + 类型 + 平台 ID、标题、截止时间、来源 URL、最后见到时间 |
| `assignment_contents` | 作业键、内容版本、原始 HTML、内容块、检查时间、抓取状态、错误 |
| `assets` | 图片哈希、文件路径、类型、尺寸、来源、验证器与检查时间 |
| `content_views` | 源版本、摘要、裁剪框、折叠块、规则版本、人工修正与复核状态 |

作业与测试必须区分键空间；手动条目继续使用已有 ID。测试解析若暂时没有可靠平台 ID，应标记身份不确定并保留来源，不能简单用标题作唯一键而合并同名测试。

数据库事务只覆盖本地写入，不能跨整个网络请求持有写锁。图片下载到临时文件，验证后原子落盘，再关联数据库；清理缓存时只删除无引用的派生文件。用户确认的规则与裁剪需要可导出备份，不应被普通清缓存操作一并删除。

新增缓存、原图、数据库附属文件均加入 `.gitignore`，脱敏测试样例单独存放，不提交真实课程材料。

### 5.2 接口改造建议

以下是拟议接口，不代表当前已存在：

| 接口 | 用途 |
| --- | --- |
| `GET /api/list?days=7&include_expired=0` | 从缓存返回平台与手动作业，并带覆盖、新鲜度和内容状态 |
| `POST /api/tasks`，`op=fetch` | 刷新列表；同范围任务去重，返回任务 ID |
| `GET /api/tasks/{id}` | 返回 `queued/running/partial/done/error/cancelled`、阶段、完成课程数、总数和结果版本 |
| `GET /api/assignments/{key}/content` | 读取已缓存内容；不存在时明确返回未就绪状态 |
| `POST /api/tasks`，`op=content` | 补齐或强制刷新指定正文；允许批量和优先级 |
| `GET /api/assets/{id}` | 返回已下载的本地图片 / 裁剪图 |
| `POST /api/assignments/{key}/view` | 保存裁剪、折叠、人工摘要，带预期源版本以防覆盖新内容 |

初期复用现有每秒轮询即可，不必为了进度引入新服务。前端把全局单个 `polling` 改为按任务 ID 管理；轮询失败显示连接状态并允许重连，不抹掉已加载结果。通过结果版本只更新发生变化的行，避免正文补齐时列表跳动。

`weekly.fetch` 目前使用 `subprocess.run(capture_output=True)`，因此仅给前端加进度字段还不够。第一版可由抓取子进程逐课写数据库中的扫描状态，服务端读取；也可后续改为结构化事件流，但不要解析人类可读 stderr 作为稳定协议。

### 5.3 内容资源的处理边界

- 不能把平台 `content_html` 原样塞进前端 `innerHTML`。由结构化块构造界面，只保留允许的标签和链接，移除脚本、事件属性、表单、iframe 等活动内容。
- 受登录保护的图片由服务端使用平台会话下载，本地页面只访问资产 ID；不把 Cookie 发给前端，也不依赖系统浏览器恰好登录。
- 下载仅接受从受信任正文解析出的允许来源，逐次检查重定向；不做任意 URL 代理。限制文件大小、解码像素数量与类型，防止异常图片耗尽资源。
- OCR 与页面文字都是数据，不能成为执行命令或修改配置的指令。
- 持续保留标题、截止时间和平台原文入口。图片、裁剪和摘要失败不应破坏这些基本信息。

## 6. 推送范围与兼容性

本次诉求优先落在“搜索结果直接显示作业内容”。**第一阶段保持现有群推送格式**，让图文内容先在控制台可靠展示。

以后如扩展群提醒，可在标题下添加一到两行有来源依据的内容摘录，图片仍优先通过平台原文入口查看。现有企业微信通道发送的是文本，图文发送应作为独立改动验证消息类型、长度、分段与去重，不能假设贴上本机图片地址就能给全班看到。

推送必须继续保留班级群与个人小群的受众区分。正文 OCR 状态不能改变名单或提交状态筛选规则；正文更新也不能自动触发额外群发。

兼容策略：

- 第一版保留现有 CLI 和 `console-legacy.bat` 的基本列表能力，新增字段使用可选值。
- 浏览器抓取保留为回退模式，HTTP 试验失败时可以切回。
- 无数据库缓存时正常全量扫描，不影响新机器首次部署。
- `server.py` 继续主要负责 I/O 和任务调度；抓取、缓存与内容规则放到独立模块，不把平台逻辑堆进 HTTP Handler。

## 8. 分阶段交付与验收

### 阶段 A：消除等待障碍，建立可信缓存

范围：真实计时、测试开关和过期项语义、严格互斥、持久化列表、缓存首屏、按课程进度、有效空态判断。

验收：

- 有缓存时，本机普通规模列表首屏目标 **1 秒内**，即使离线也能查看并识别数据时间。
- 改变展示天数不启动新的平台扫描；缺少所需覆盖时明确提示并刷新。
- 连续点击搜索不会堆积重复抓取；定时与控制台竞争时不会越过锁。
- “不抓在线测试”确实不发测试栏目请求；默认模式仍包含测试。
- 有效空课程不重复跑整门课；登录页、坏表格不能判为空课。
- 同课程集合、同测试开关、同网络条件下，比较修改前后至少 5 轮；确认条目 ID、截止时间、覆盖范围一致后，争取列表完整刷新中位数降低 **30%**。这是验收目标，达不到时以阶段计时定位，不靠缩减覆盖凑速度。

### 阶段 B：所有搜索结果可自动获得图文内容

范围：正文批量任务、缓存、图文块渲染、原图、多区域手动裁剪、内容版本失效。

验收：

- 纯图片作业不再显示成“没有正文”；图文顺序和题号保留。
- 冷启动先显示列表，再补正文；正文数量增加不阻塞列表可用。
- 已缓存内容打开目标 **500 毫秒内**，再次搜索不重复下载未过期正文。
- 图片裁剪可撤销、可查看原图；重开控制台后仍保留。
- 老师改正文、同 URL 换图片、用户修改期间后台更新，都不会无提示地沿用旧裁剪。
- 正文请求失败仅影响对应条目；其他作业、预览和手动录入继续可用。

### 阶段 C：减少重复要求与人工裁剪

范围：课程通用要求规则、OCR 区域建议、可选复杂图片处理。

准备覆盖实际情况的本地样本集：纯文字、纯图片、图文混排、重复要求、新增例外、复杂公式、低清晰度、附件、多区域作业。建议先收集 20–30 份有代表性的样本，并由用户标注真正应展示的区域；样本不足时记录空缺，不声称已经验证。

验收重点是“不能少题”：

- 人工标注的必做题号、页码、公式和附图，在每份验收样本中都能从默认展示区域看到。
- 无法确定的图片退回原图，不输出一个看似简洁但缺题的裁剪结果。
- 重复要求识别的“误折叠关键内容”单独统计；发现这类错误时停用相应自动规则。
- 记录首次处理时间、CPU/内存、缓存命中率及需要人工调整的比例，再决定是否值得启用更复杂模型。

### 需要覆盖的回归场景

| 场景 | 预期 |
| --- | --- |
| 个人已提交某门作业 | 班级提醒仍包含该条 |
| 新增作业、改截止时间、撤回作业 | 完整成功扫描后正确更新；失败不误删 |
| 课程只有测试、没有普通作业 | 正常统计测试，不因普通作业 0 条整体判失败 |
| 所有课程确实为空 | 有完整空态证据才能视为有效空结果 |
| 分页或平台页面结构变化 | 未确认完整前不覆盖整课快照，不静默漏页 |
| 账号变化、黑名单移出、测试范围扩大 | 旧缓存不冒充新范围的完整数据 |
| 平台失效、单课超时、正文超时 | 展示具体失败范围并保留旧数据，发布按覆盖策略处理 |
| 定时任务与界面同时刷新 | 串行、任务可见、无课程串用 |
| 重复要求中出现“本周改为”或新增题号 | 变化保留，不能整段折叠 |
| 恶意 HTML、超大图片、无效附件 | 安全降级，界面和基本列表仍可用 |

本次仅新增设计文档，未执行上述性能实验或回归测试。

## 9. 首个可用版本的边界

建议首个版本完成 **阶段 A + 阶段 B**：打开即有结果、扫描可见进度、列表不等正文、文字与原图自动展示、图片区域可以手动选择并持久保存。这已能直接改善两个日常痛点。

HTTP 取数、OCR 和自动裁剪分别验证、分别启用。即使它们暂时没有达到预期，首个版本仍然有明确价值，且能为后续自动化积累真实图片样本和人工选择依据。
